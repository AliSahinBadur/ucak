\chapter{Testing and QA}
\label{ch:testing}

There are two layers of checking in this project, and they answer different
questions:

\begin{itemize}
\item \textbf{the pytest suite} --- does the code still do what it says? Offline,
deterministic, fast, and part of CI.
\item \textbf{the check scripts} --- is retrieval and review still \emph{good}?
Scored against golden sets over a real corpus, run by hand when something
changes.
\end{itemize}

\section{The pytest suite}

\begin{shellblock}
& '.venv\Scripts\python.exe' -m pytest -q

# with coverage
& '.venv\Scripts\python.exe' -m pytest -q --cov=app --cov-report=term
\end{shellblock}

The suite needs no model, no Ollama and no network.

\subsection{The conftest contract}

\file{tests/conftest.py} pins the environment \textbf{at import time}, before
anything under \file{app} is imported:

\begin{pyblock}
TEST_DATA_DIR = Path(tempfile.mkdtemp(prefix="ucak-test-data-"))
os.environ["BIG_AGENT_DATA_DIR"] = str(TEST_DATA_DIR)
os.environ["EMBEDDING_BACKEND"] = "token-hash"
os.environ["LLM_ENABLED"] = "false"
# ... every other LLM and the CATIA skill disabled ...

from app.db.session import SessionLocal, engine, init_db  # noqa: E402
\end{pyblock}

This ordering is load-bearing, not stylistic. \file{app/db/session.py} builds the
engine from \code{Settings} when it is imported, and \code{get\_settings()} is
cached, so a fixture body cannot redirect the database after the fact.

Two rules follow, and both are absolute:

\begin{enumerate}
\item \textbf{Never import \code{app} above that environment block.}
\item \textbf{Never add a test that reaches the network or loads a
sentence-transformers model.}
\end{enumerate}

At session end the engine is disposed before the temp directory is removed ---
Windows will not delete a database file while a pooled connection still holds it.

The suite spans parsing and chunking, text cleaning and normalization, ingest and

\section{The check scripts}

All of them read the corpus in the \textbf{current} \env{BIG\_AGENT\_DATA\_DIR}
and print the data directory and document count on their first line. Read that
line before reading the results --- it is the difference between checking your
real corpus and checking a demo folder you set up an hour ago.

\subsection{Smoke checks}

\begin{shellblock}
& '.venv\Scripts\python.exe' scripts\run_smoke_checks.py
& '.venv\Scripts\python.exe' scripts\run_smoke_checks.py --base-url http://127.0.0.1:8001
\end{shellblock}

Hits a \textbf{running} instance and verifies the endpoints answer.

\subsection{QA and retrieval regression}

\begin{shellblock}
& '.venv\Scripts\python.exe' scripts\run_qa_checks.py
\end{shellblock}

Beyond the pass/fail gate, this scores retrieval with the Haystack evaluators for
the in-house stack (\code{v2}) and the Haystack pipeline (\code{v3}) side by
side:

\begin{shellblock}
Summary: 22 passed, 0 failed (gate: v2)

version     cases   recall@k      MRR     nDCG  provider
v2             22     100.0%    0.977    0.983  token-hash-v1
v3             22      90.9%    0.886    0.892  haystack:3.1.0
\end{shellblock}

Options: \code{--cases} (a different case file), \code{--k} (recall cutoff,
default 5), \code{--no-metrics} (gate only), \code{--no-persist} (do not write
the run). Each run is written to \file{data/qa\_runs/<timestamp>.json}, so a
regression reads as a trend rather than a single bad afternoon. The gate still
runs on its own if \code{haystack-ai} is not installed.

\subsection{Portable document references}

Cases name a \textbf{report}, not a database id. Pinning
\code{"document\_id": 9} resolves only against one operator's
\file{data/app.db}: re-ingest the corpus in a different order and the suite
silently checks the wrong reports.

A reference is one of:

\begin{jsonblock}
"2025-BIG-E-NVH-01"
{"report_code": "2025-BIG-E-NVH-01"}
{"title_contains": ["fren", "pedal"]}
{"document_id": 9}
\end{jsonblock}

\code{DocumentReferenceResolver} resolves the first three through the catalog and
the document titles and file names. The last is the legacy pin, kept so an
un-migrated file still runs --- and surfaced as the portability hazard it is.

\subsection{Report review regression}

\begin{shellblock}
& '.venv\Scripts\python.exe' scripts\run_report_review_checks.py --precision
\end{shellblock}

Runs the golden set in \file{test\_cases/report\_review\_cases.json} --- keyed by
report code, resolved the same way --- and reports the per-rule confirm rate
alongside the gate.

\section{The synthetic corpus}

For clicking through the application the way an operator would, without touching
real company documents:

\begin{shellblock}
& '.venv\Scripts\python.exe' scripts\generate_sample_reports.py --clean
& '.venv\Scripts\python.exe' scripts\verify_sample_reports.py
\end{shellblock}

Everything in the corpus is invented --- fictional vehicles (\code{SYN-Bus 12},
\code{SYN-Van 3}), fictional people, report codes prefixed \code{2026-SYN-} ---
so nothing can be mistaken for a real document. It writes 16 files plus a catalog
to \file{sample\_reports\textbackslash} (gitignored);
\code{--out D:\textbackslash demo} puts them elsewhere.

Each report exercises one known part of the engine. Four are clean, one per
discipline; the rest each carry exactly one planted defect, so when a finding
appears you know whether it is the one you were looking for.
\file{verify\_sample\_reports.py} ingests the corpus into a \textbf{throwaway}
database, prints the findings per report, and ends with:

\begin{shellblock}
OK - every report matched its expectation
\end{shellblock}

Use a separate data folder so the demo does not land in your working database:

\begin{shellblock}
$env:BIG_AGENT_DATA_DIR = ".\data_demo"
\end{shellblock}

\subsection{Walking the corpus}

\textbf{Load it.} Sort by name so the original is ingested before its copy:

\begin{shellblock}
Get-ChildItem sample_reports\*.pdf, sample_reports\*.docx | Sort-Object Name | ForEach-Object {
  curl.exe -s -X POST http://127.0.0.1:8000/ingest -F "file=@$($_.FullName)"
}

curl.exe -s -X POST http://127.0.0.1:8000/catalog/import -F "file=@sample_reports\katalog_SYN.csv"
curl.exe -s -X POST http://127.0.0.1:8000/catalog/reconcile-documents
\end{shellblock}

15 files ingest and the copy comes back \code{"status":"duplicate"} --- caught
by its hash before parsing. The catalog import creates 15 rows and the reconcile
links each to its file. The link matters for review: the catalog's
\code{discipline} column is what the \code{auto} profile reads first.

\textbf{Ask for a review.} The wording reaches the review engine only through
the intent router, which looks for \code{raporu kontrol et},
\code{rapor kontrolu}, \code{kalite kontrolu}, \code{teknik kontrol},
\code{raporda hata var mi}, \code{raporda eksik var mi} or
\code{rapor uygun mu}. Anything else goes to ordinary retrieval.

\begin{shellblock}
$body = '{"message":"Bu raporu kontrol et","document_ids":[8],"assistant_mode":"report"}'
curl.exe -s -X POST http://127.0.0.1:8000/chat -H "Content-Type: application/json" -d $body
\end{shellblock}

\textbf{Compare revisions.} Select both revisions and satisfy two conditions at
once --- a review phrase from above, plus \code{revizyon} and a comparison verb
(\code{karsilastir}, \code{kiyasla}, \code{yeni bulgu}, \code{giderilen},
\code{devam eden}):

\begin{shellblock}
Bu raporu kontrol et ve revizyonlari karsilastir
\end{shellblock}

\code{Bu iki revizyonu karsilastir} alone does \textbf{not} work; it routes to
generic document comparison instead.

\textbf{Run the golden set against this corpus.} The shipped case file names the
real \code{2025-BIG-*} reports, so against the synthetic corpus every case
reports SKIP --- and a run where everything skipped exits non-zero rather than
claiming a green build. A companion file covers the synthetic reports:

\begin{shellblock}
& '.venv\Scripts\python.exe' scripts\run_report_review_checks.py `
    --cases test_cases\report_review_cases_sample.json
# Summary: 13 passed, 0 failed, 0 skipped
\end{shellblock}

\textbf{Note on semantic search.} \code{mode=semantic} returns nothing on a
default install: the \code{token-hash} fallback is a deterministic stand-in, not
a real model. \code{keyword} and \code{hybrid} work with no model at all. Point
\env{EMBEDDING\_MODEL\_PATH} at a Qwen3 model and rebuild embeddings for real
semantic hits.

\textbf{Start over.} Delete the data folder and regenerate:

\begin{shellblock}
Remove-Item -Recurse -Force .\data_demo
& '.venv\Scripts\python.exe' scripts\generate_sample_reports.py --clean
\end{shellblock}

\begin{callout}{Known issue this corpus reproduces}
\file{GEN-05.pdf} writes \code{TARİH:} on its cover with the Turkish dotted
capital I (U+0130), and the metadata check misses it:
\code{ReportQualityService.\_normalize\_text} casefolds first, which turns
\code{İ} into \code{i} plus a combining dot, and then applies a translate map
that no longer contains U+0130 --- so \code{TARİH} normalizes to
\code{tari\textbackslash u0307h} and the alias \code{tarih} never matches. This
affects every uppercase Turkish keyword containing \code{İ}, real report covers
included. \file{app/text/normalize.py} already does the right thing (NFKD plus
stripping combining marks), so the fix is to strip combining marks in
\code{\_normalize\_text} too. The other files use ASCII \code{TARIH} to keep the
corpus clean.
\end{callout}

\section{Adding a discipline review check}

Because discipline rules are data, adding one is a data edit plus a golden case:

\begin{enumerate}
\item edit or add the file under
\file{app/rules/profiles/<discipline>.json};
\item add a case to \file{test\_cases/report\_review\_cases.json} naming a report
by code; and
\item run \file{scripts\textbackslash run\_report\_review\_checks.py}.
\end{enumerate}

\file{profile\_catalog.py} validates every profile file at import time ---
unknown keys included --- so a typo fails the import with the file and the
offending path named, rather than becoming a rule that quietly never fires. The
full file schema, key by key, is in Section~\ref{sec:profile-schema}.

Two flags are worth knowing when you are iterating on rules:

\begin{shellblock}
# only the per-rule confirm rate, no golden cases
& '.venv\Scripts\python.exe' scripts\run_report_review_checks.py --precision-only

# lower the decision floor while a rule is still young
& '.venv\Scripts\python.exe' scripts\run_report_review_checks.py --precision --min-decisions 3
\end{shellblock}

\section{Continuous integration}

\file{.github/workflows/ci.yml} runs on pushes to \code{main} and
\code{improvement} and on every pull request, with two jobs:

\begin{description}
\item[\code{test}] \code{uv sync --group dev} followed by \code{uv run pytest -q},
resolved against the committed \file{uv.lock}.
\item[\code{requirements}] Installs \file{requirements.txt} on a clean Python
3.11 and imports the application --- the guard against \file{pyproject.toml} and
\file{requirements.txt} drifting apart.
\end{description}

Keep the suite offline and model-free: a test that downloads a model passes on a
workstation with a warm cache and fails in CI, which is the worst of both worlds.
